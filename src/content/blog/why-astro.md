我之前是用手写 HTML 的方式做页面的：一个 `index.html`，一个关于页，几个练习页。刚开始觉得挺好，每个标签都自己敲，能记住。

问题出现在**页面变多之后**。

## 手写 HTML 的真实成本

假设我想给全站导航加一个"标签"入口。如果有 10 个页面，我就要打开 10 个文件，找到导航那一段，粘贴同样的代码。

这还不算最糟的。最糟的是某一次我漏改了一个页面，然后那个页面的导航跟别的地方长得不一样——而我要过好几天才会发现。

这不是"手写不够努力"的问题。这是**同样的信息存了 10 份**，改的时候必然不一致。

## 静态生成器做的事

Astro 的思路很简单：**你写一次模板，构建时把它套用到每个页面**。

于是：

| 东西 | 谁来做 |
| --- | --- |
| 页面骨架、导航、页脚 | 我写一次，机器复制 |
| CSS | 我全手写，机器只负责压缩打包 |
| 新文章 | 我写 Markdown，机器生成 HTML |
| 文章列表、RSS、sitemap | 机器全权负责 |

注意第二行：**样式一点没少写**。生成器接走的是"维护重复内容"这件事，不是我该练的基本功。

## 发文流程变成了这样

以前：复制一个 HTML，改标题，改正文，改日期，改列表页。

现在：新建一个文件。

```bash
npm run new -- my-new-post
```

然后在文件开头填几个字段：

```yaml
---
title: 文章标题
description: 一句话摘要，会显示在列表和搜索结果里
pubDate: 2026-10-20
tags: ['技术']
---
```

正文就是普通的 Markdown。`##` 是二级标题，代码用三个反引号包起来，链接用方括号加圆括号。写的内容和最终的排版之间，不用再操心 HTML 结构。

## 一个容易踩的坑

这个站点部署在 GitHub Pages 的**项目页**上，地址是 `https://lizhanyiawa.github.io/kirara-blog/`，多了一层 `/kirara-blog/` 前缀。

Astro 会给它自己处理的资源（CSS、图片）自动加上这个前缀，但**不会给手写的字符串链接加**。所以站内链接不能写成 `/about/`，必须走统一的助手函数：

```javascript
import { url } from '../config';

// 正确
url('about/');   // -> /kirara-blog/about/

// 错误：构建不会报错，但点击会 404
'/about/';
```

这是 GitHub Pages 项目页最常见的 404 来源。

## 值得吗

对我来说值得。多出来的代价是一个构建步骤和一层依赖（Node 版本有一定要求），换来的是发文时不用再想"我还有几个地方没改"。
